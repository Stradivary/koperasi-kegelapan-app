# Requirements Document

## Introduction

This feature converts the application from a TanStack Start SSR deployment on Cloudflare Workers into a fully static SPA with aggressive PWA precaching. The goal is complete offline readiness from first load — every asset is downloaded at service worker install time. The deployment is split into a static SPA on Cloudflare Pages and a separate API Worker for backend routes.

## Glossary

- **SPA**: Single-Page Application — a client-side rendered application served as static HTML, JS, and CSS assets with no server-side rendering.
- **Service_Worker**: A browser-registered script that intercepts network requests and manages caching for offline support.
- **Precache_Manifest**: The list of all static assets (JS chunks, CSS, fonts, images, HTML) that the Service Worker downloads and caches at install time.
- **VitePWA_Plugin**: The `vite-plugin-pwa` Vite plugin that auto-generates a Workbox-based service worker and injects registration code.
- **GenerateSW**: The Workbox strategy where the service worker is entirely generated by the build tool from configuration, requiring no custom SW source file.
- **Cloudflare_Pages**: Cloudflare's static site hosting platform that serves pre-built assets from edge locations.
- **API_Worker**: A dedicated Cloudflare Worker that handles server-side API routes (authentication, session grants, policy, reconciliation, tenant management, superadmin).
- **Build_Pipeline**: The Vite build process that produces the final static output for deployment.
- **Navigate_Fallback**: The service worker behavior of serving a cached HTML shell for all navigation requests, enabling client-side routing offline.

## Requirements

### Requirement 1: Remove SSR Infrastructure

**User Story:** As a developer, I want the SSR infrastructure removed, so that the application builds as a fully static SPA without server-side rendering dependencies.

#### Acceptance Criteria

1. THE Build_Pipeline SHALL produce only static client assets (HTML, JS, CSS, fonts, images) with no server-side entry point.
2. WHEN the build completes, THE Build_Pipeline SHALL output a single `index.html` file that bootstraps the client-side application.
3. THE Build_Pipeline SHALL exclude the `@cloudflare/vite-plugin` SSR environment configuration from `vite.config.ts`.
4. THE Build_Pipeline SHALL replace `@tanstack/react-start` with `@tanstack/react-router` SPA-mode configuration.
5. THE Build_Pipeline SHALL remove the `tanstackStart()` plugin call from `vite.config.ts`.

### Requirement 2: Remove Custom Service Worker

**User Story:** As a developer, I want the custom service worker code removed, so that the VitePWA plugin's generateSW strategy manages all caching without manual SW maintenance.

#### Acceptance Criteria

1. THE Build_Pipeline SHALL exclude the `src/sw.ts` file from the project source.
2. THE Build_Pipeline SHALL exclude the `scripts/build-sw.mjs` build script from the project.
3. THE Build_Pipeline SHALL rely solely on VitePWA_Plugin generateSW configuration for service worker generation.
4. WHEN the application loads, THE SPA SHALL NOT execute manual `navigator.serviceWorker.register()` calls in application code.
5. THE VitePWA_Plugin SHALL handle service worker registration via the `injectRegister: 'auto'` configuration.

### Requirement 3: Full Precaching of Static Assets

**User Story:** As a user, I want all application assets downloaded on first visit, so that the entire application works offline without needing to visit each route individually.

#### Acceptance Criteria

1. WHEN the Service_Worker installs, THE Service_Worker SHALL download and cache every JS chunk in the Precache_Manifest.
2. WHEN the Service_Worker installs, THE Service_Worker SHALL download and cache every CSS file in the Precache_Manifest.
3. WHEN the Service_Worker installs, THE Service_Worker SHALL download and cache every font file (woff2, woff, ttf) in the Precache_Manifest.
4. WHEN the Service_Worker installs, THE Service_Worker SHALL download and cache every image file (png, svg, ico) in the Precache_Manifest.
5. WHEN the Service_Worker installs, THE Service_Worker SHALL download and cache the `index.html` shell.
6. THE VitePWA_Plugin SHALL configure workbox `globPatterns` to match all static asset types: `**/*.{js,css,html,ico,png,svg,woff,woff2,ttf,json}`.
7. THE VitePWA_Plugin SHALL set `maximumFileSizeToCacheInBytes` to at least 5 MB to accommodate large chunks.

### Requirement 4: Offline Navigation Support

**User Story:** As a user, I want to navigate between all application routes while offline, so that the full UI remains functional without internet connectivity.

#### Acceptance Criteria

1. THE Service_Worker SHALL configure `navigateFallback` to serve the cached `index.html` for all navigation requests.
2. THE Service_Worker SHALL configure `navigateFallbackDenylist` to exclude paths matching `/api/` from the navigation fallback.
3. WHEN a user navigates to any client route while offline, THE Service_Worker SHALL respond with the cached `index.html` shell.
4. WHEN the cached `index.html` loads, THE SPA SHALL use client-side routing to render the requested route from precached JS chunks.

### Requirement 5: API Route Separation

**User Story:** As a developer, I want API routes deployed as a separate Cloudflare Worker, so that the static SPA and backend logic have independent deployment lifecycles.

#### Acceptance Criteria

1. THE API_Worker SHALL serve all routes under the `/api/` path prefix, including: `/api/session-grant`, `/api/policy`, `/api/reconcile`, `/api/accounts`, `/api/auth/*`, `/api/superadmin/*`, `/api/tenants/*`.
2. THE API_Worker SHALL retain access to the D1 database binding (`DB`) and environment variables (`SESSION_MASTER_KEY`).
3. THE API_Worker SHALL have a dedicated wrangler configuration file separate from the static SPA deployment.
4. THE Cloudflare_Pages deployment SHALL serve only static assets and SHALL NOT include server-side route handlers.
5. THE SPA SHALL reference the API_Worker base URL for all API requests, configurable via an environment variable or build-time constant.

### Requirement 6: Vite Configuration Cleanup

**User Story:** As a developer, I want the Vite configuration simplified to reflect the static SPA build, so that unnecessary SSR plugins and configurations are removed.

#### Acceptance Criteria

1. THE Build_Pipeline SHALL remove the `@cloudflare/vite-plugin` import and `cloudflare()` plugin call from `vite.config.ts`.
2. THE Build_Pipeline SHALL remove the `rollupOptions.external` entry for `cloudflare:` modules from `vite.config.ts`.
3. THE Build_Pipeline SHALL configure `vite-plugin-pwa` with `strategies: 'generateSW'` and `registerType: 'autoUpdate'`.
4. THE Build_Pipeline SHALL configure `vite-plugin-pwa` with `injectRegister: 'auto'` to handle SW registration without manual code.
5. THE Build_Pipeline SHALL retain the `@vitejs/plugin-react`, `@tailwindcss/vite`, and `@tanstack/router-plugin` plugins.

### Requirement 7: PWA Update Mechanism

**User Story:** As a user, I want to be notified when a new version of the application is available, so that I can update to the latest version with fresh cached assets.

#### Acceptance Criteria

1. WHEN a new Service_Worker is detected, THE SPA SHALL display an update prompt to the user.
2. WHEN the user accepts the update, THE Service_Worker SHALL activate the new version and reload the page.
3. THE VitePWA_Plugin SHALL configure `registerType: 'autoUpdate'` to enable automatic update detection.
4. THE SPA SHALL retain the existing `PwaUpdatePrompt` component for user-facing update notifications.

### Requirement 8: Deployment Configuration

**User Story:** As a developer, I want clear deployment configurations for both the static SPA and the API Worker, so that each can be deployed independently.

#### Acceptance Criteria

1. THE Cloudflare_Pages deployment SHALL use the `dist/` (or `dist/client/`) output directory as the publish directory.
2. THE API_Worker SHALL have a `wrangler.jsonc` (or `wrangler.api.jsonc`) configuration with the D1 binding, compatibility flags, and entry point.
3. THE Build_Pipeline SHALL update `package.json` scripts to reflect the split deployment: a static build command and a separate API deploy command.
4. THE Cloudflare_Pages deployment SHALL configure a `_redirects` or `_routes.json` file to proxy `/api/*` requests to the API_Worker, OR the SPA SHALL use an absolute API base URL.
